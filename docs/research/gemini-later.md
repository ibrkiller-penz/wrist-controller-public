# 나중에 Gemini 음성을 넣는다면 — 메모리 예산과 구조 (메모, 2026-10-17)

> 결정(2026-10-17, 사용자 "메모리 빠듯하면 Gemini 빼자"): **지금은 만들지 않는다.** 음성 기능 전체(WakeNet·마이크·누르고 말하기·본인 목소리 next)도 뺐다.
> 다음 슬라이드는 BOOT 짧게·화면 탭·손목 튕김만. 이 문서는 나중에 다시 꺼낼 때의 출발점이다.

## 1. 지금 메모리 (ESP32-C6, 내부 SRAM 512KB, PSRAM 없음)

| 시점 | 내부 RAM 여유 | 최대 블록 | 근거 |
| --- | --- | --- | --- |
| 음성까지 모두 켠 뒤(dev.75008c8) | 약 117KB | 약 100KB | docs/bootlog_dev2_v0.0.0-dev.75008c8.txt |
| BLE 까지만(같은 로그, 음성 전) | 약 184KB | 약 168KB | 같은 로그 '[메모리 BLE 후]' |
| 음성 뺀 뒤(이번 빌드) | 실측 필요 — BLE 후 값에서 IMU·직렬 태스크 스택(약 10KB)을 뺀 정도로 예상 | | 시계에 올린 뒤 '[메모리 …]' 로그 |

## 2. Gemini 를 붙이면 드는 것(대략)

| 항목 | 내부 RAM |
| --- | --- |
| Wi-Fi 드라이버·LwIP(STA, 버퍼 최소) | 60~80KB |
| TLS(mbedTLS, HTTPS/WSS 한 연결, 단편화 줄여도) | 35~45KB |
| BLE HID(NimBLE, 이미 사용 중) | 이미 위 '여유'에 반영 |
| LVGL 화면(이미 사용 중) | 이미 위 '여유'에 반영 |
| 마이크 버퍼(16kHz 모노, 100ms × 2) + 인코딩 | 약 6~10KB |

→ 음성(WakeNet)을 빼고도 **남는 건 약 20KB 안팎**. TLS 핸드셰이크 순간 최대 블록(약 16KB 이상 연속)이 모자라면 바로 실패하고, Wi-Fi·BLE 동시 사용(코엑지스턴스)은 지연과 끊김이 생긴다. 지금 구조로는 넣지 않는 것이 맞다.

## 3. 나중에 한다면 — 구조 후보

1. **폰이 Gemini 를 맡는다(권장)**: 시계는 지금처럼 BLE HID 만. 폰 앱/웹이 마이크·Gemini API 를 쓰고, 결과(다음/이전)를 PC 로 보내거나 시계에 BLE 로 짧은 명령만 보낸다. 시계 메모리 증가 0, API 키도 시계에 두지 않는다.
2. **PC 가 Gemini 를 맡는다**: PC 쪽 작은 프로그램이 마이크를 듣고 키를 누른다. 'PC 설치 프로그램 없음' 원칙과 부딪힌다.
3. **시계가 직접(Wi-Fi + TLS)**: 위 표대로 여유가 거의 없다. 하려면 ① 화면 버퍼 줄이기(40줄 → 20줄), ② BLE 와 Wi-Fi 를 동시에 켜지 않기(누르는 동안만 Wi-Fi), ③ PSRAM 있는 보드(S3)로 바꾸기 중 하나가 필요하다.

## 4. 다시 꺼낼 때 순서

1. 이번 빌드를 시계에 올려 부팅 로그 '[메모리 …]' 로 실제 여유·최대 블록을 적는다.
2. 1번(폰) 구조로 시뮬레이터에서 먼저 흐름을 만든다(코어에는 `voice` 입력을 다시 넣지 않고, 폰이 PC 로 바로 보낸다).
3. 시계 직접 방식은 PSRAM 보드로 바꿀 때만 다시 검토한다.
